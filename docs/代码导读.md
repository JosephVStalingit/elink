# 代码导读（写给只会基础 Java 的二次开发者）

这份文档不假设你会 Minecraft 模组开发，也不假设你懂 WebRTC。读完之后你应该能回答三个问题：
**代码分成哪几块**、**一次"朋友连上我的世界"到底走了哪些步骤**、**想改某个行为该动哪个文件**。

---

## 1. 先理解要解决的问题

Minecraft 的「对局域网开放」只能让**同一个局域网**里的电脑连进来。本模组要做的事是：把这条局域网连接
"搬"到互联网上，而且**不经过任何中转服务器**——数据在两位玩家的电脑之间直连。

为此需要两样东西：

1. **先让两端互相找到**：这一步叫「信令」（signalling），只在建立连接前用一下，数据量极小。
   本模组用 MQTT 完成：大家约定一个"房间"（一串主题名），把建立连接需要的信息贴在那里。
2. **再建立一条直连的数据管道**：这一步用 WebRTC 的 DataChannel。它像一条双向 TCP 连接，
   但由两端的浏览器内核（这里是 WebRTC 原生库）负责穿透 NAT、加密、重传。

最后，把 Minecraft 的 TCP 流量塞进这条管道，这一步叫「隧道」（tunnel）。

> 记住一句话：**MQTT 只负责"约见面"，见面之后所有游戏数据都走 WebRTC 直连。**

---

## 2. 一句话看懂数据流

```
                ① 信令（MQTT，只在建连前用）
   房主  <────────────────────────────────────────>  朋友
     │                                                │
     │ ② WebRTC DataChannel（直连，承载全部游戏数据）   │
     └────────────────────────────────────────────────┘
     ▲                                                ▲
     │ ③ 隧道：把 TCP 连接拆成"帧"塞进通道               │
     │                                                │
  本地游戏端口 25565                               本地监听端口（自动分配）
  （房主"对局域网开放"的端口）                     （朋友在多人游戏列表里看到的地址）
```

再具体一点：

| 步骤 | 房主侧 | 朋友侧 |
| --- | --- | --- |
| 1 | `/elink host` → 得到房间码 + 房间密钥，聊天栏给出邀请命令 | — |
| 2 | — | `/elink join <房间码> <密钥>`：连上同一个 MQTT 房间，并开始本地监听 |
| 3 | 收到对方的 `hello` → 要求对方证明账号（若设了好友名单）→ 通过后开始 WebRTC 协商 | 应答账号挑战 → 参与 WebRTC 协商 |
| 4 | 协商完成，双方各得到一条数据通道 | 同左 |
| 5 | — | 游戏里"多人游戏"列表出现条目，玩家点进去 → 本机 TCP 连接到"本地监听端口" |
| 6 | 数据通道上收到 `OPEN` 帧 → 拨号 `127.0.0.1:25565`（自己开的局域网世界） | 把这条 TCP 连接的内容打成 `DATA` 帧发过去 |
| 7 | 之后就是纯字节转发，Minecraft 协议本身完全不知道中间有隧道 | 同左 |

## 3. 包的职责（建议按表格顺序阅读）

| 包 | 里面有什么 | 一句话职责 |
| --- | --- | --- |
| `com.example.elink` | `ELink` | 入口：加载配置、探测 WebRTC、注册命令、按配置自动加入房间 |
| `config` | `ELinkConfig`、`InstallId`、`SecretStore`、`WindowsKeyProtector` | 读写 `config/elink.properties`；安装 ID；账号令牌的加密存储（Windows 上由 DPAPI 保护） |
| `platform` | `Platform` | **唯一**处理 Fabric / Forge / NeoForge 差异的地方（配置目录、模组版本、是否客户端、命令注册时机） |
| `command` | `ELinkCommand` | `/elink` 全部子命令：`host`/`join`/`leave`/`status`/`login`/`whoami`/`friends` |
| `client` | `ELinkClient` | 读"对局域网开放"的端口，交给通用代码（只有客户端会加载这个类） |
| `lan` | `LanAnnouncer` | 每 1.5 秒广播一次假局域网信息，让朋友在多人游戏列表里看到条目 |
| `signalling` | `SignalMessage`、`SignallingClient`、`RoomSecret` | MQTT 传输、JSON 消息格式、房间密钥的 HMAC 证明 |
| `rtc` | `WebRtcEngine`、`PeerSession` | 包装 webrtc-java：创建工厂、一个对端一个连接、offer/answer/ICE、数据通道 |
| `net` | `P2PSession` | 会话编排：加入房间、决定谁先发起、账号证明状态机、把消息分发给对应的对端 |
| `tunnel` | `TunnelFrame`、`TunnelStream`、`TunnelMultiplexer`、`TunnelSession` | 把多条 TCP 连接复用到一条数据通道上（含分片、背压、流生命周期） |
| `identity` | `LittleSkinClient`、`IdentityService`、`PlayerIdentity`、`ResultCache` | 账号服务：登录、刷新令牌、`join`/`hasJoined` 挑战应答、验证结果缓存 |

阅读顺序建议：`ELink` → `command/ELinkCommand` → `net/P2PSession` → `signalling/*` → `rtc/PeerSession` →
`tunnel/*` → `identity/*` → `config/*`。

## 4. 一次联机的完整调用链

**房主敲 `/elink host`：**

1. `ELinkCommand.host` → 若还没设房间密钥，用 `RoomSecret.generate()` 生成并写进配置；
2. `ELink.ensureInRoom` → 创建 `P2PSession` 并 `join()` → `SignallingClient.connect()` 连上 MQTT，
   订阅 `elink/<房间>` 与 `elink/<房间>/presence`；
3. 连接成功后广播 `hello`（带 `hosting=true`）；
4. `ELink.startHosting` → `TunnelSession.startHost(游戏端口)`：记住"收到的流要转发到哪个本地端口"；
5. `P2PSession.setHosting(true)`：告诉房间"我这里有世界可进"。

**朋友敲 `/elink join 房间码 密钥`：**

1. `ELinkCommand.join` → 把房间码与密钥写进配置（密钥用于给每条消息签名）；
2. `ELink.ensureInRoom` → 同上连上 MQTT；
3. `ELink.startJoining` → `TunnelSession.startGuest(0)`：在本机 `127.0.0.1` 上**申请一个空闲端口**开始监听；
4. 两边互相看到 `hello`：
   - 房主若设了好友名单，会发 `challenge`；朋友用自己令牌调 LittleSkin 的 `join`，回 `challenge_response`；
     房主再用 `hasJoined` 核实，通过后发 `verified`；
   - `P2PSession.onPeerReadyToNegotiate` 比较双方安装 ID，**小的一方**发 offer（避免双方同时发）；
5. offer/answer/ICE 通过 MQTT 交换 → `PeerSession` 把它们喂给 WebRTC → 数据通道打开；
6. 各自的 `LanAnnouncer` 开始广播，朋友在多人游戏列表里看到 `易联 <房间码> - <房主>`。

**玩家点列表进入：**

1. 游戏客户端 TCP 连到朋友的"本地监听端口"；
2. `TunnelSession.acceptLoop` 接住连接 → 挑一个可用的对端（优先声明 `hosting` 的）→
   `TunnelMultiplexer.openLocalStream`：分配 stream id、发 `OPEN` 帧、启动读写线程；
3. 房主收到 `OPEN` → `TunnelMultiplexer.acceptRemoteStream`：连到自己 `127.0.0.1:25565`；
4. 之后两个方向都是"读到字节 → 切成 ≤16 KiB → 打成 `DATA` 帧 → 发送"，对端收到后写进自己的 socket；
5. 任何一端关闭 socket，就发 `CLOSE` 帧，对端也关闭对应 socket。

## 5. 想改 X 就看 Y（二次开发指引）

| 我想…… | 该改哪里 | 备注 |
| --- | --- | --- |
| 换一个 MQTT 服务器 | 配置 `broker` | 或改 `ELinkConfig.DEFAULT_BROKER_URI` 的默认值 |
| 固定加入方的本地端口 | 配置 `local-port`；留 `0` 就是自动挑空闲端口 | 逻辑在 `TunnelSession.startGuest` |
| 改房间密钥长度 | `RoomSecret.LENGTH`（十六进制字符数） | 改完两端都要重开房间 |
| 加一种新的信令消息 | `SignalMessage.Type` 加枚举值 → `P2PSession.onMessage` 的 `switch` 加分支 → 写一个 `handleXxx` 方法 | 发送时会由 `publish()` 自动签上 proof，不用自己处理 |
| 改隧道帧格式 | `TunnelFrame`（帧布局）+ `TunnelMultiplexer`（收发）+ `TunnelStream`（分片） | **两端必须同时升级**，否则不兼容 |
| 支持其它操作系统的原生库 | `gradle.properties` 的 `webrtc.natives.classifier`（`windows-x86_64`、`linux-x86_64`、`macos-aarch64` 等），并在 `build.gradle.kts` 里对每个平台多加一份 `add("include", …)` | 原生 jar 会被打进模组 jar |
| 加一个新命令 | `ELinkCommand.build()` 里注册 + 写一个私有静态方法 | 用 `reply(source, "文字")` 回话；后台线程回话用 `replyLater` |
| 加一个新加载器 | `settings.gradle.kts` 的 `mc(...)` + `Platform` 加条件分支 + `ELink` 入口加条件分支 | 还要补 `mods.toml` 之类的元数据文件 |
| 换账号服务（LittleSkin 兼容） | 配置 `littleskin-url` | 端点清单见 `identity/LittleSkinClient` 的类注释 |
| 调整账号验证缓存时间 | 配置 `identity-cache-minutes`（`0` = 不缓存） | 默认 10 分钟，用来少打扰账号服务（有每分钟 60 次的限额） |
| 让日志更啰嗦 | 把对应位置的 `LOGGER.debug` 临时改成 `info` | 各模块日志名见第 7 节 |

## 6. 线程模型（最容易踩坑的地方）

| 谁 | 在哪里 | 可以做什么 | 不要做什么 |
| --- | --- | --- | --- |
| 游戏主线程 | 命令回调、世界逻辑 | 调用 `ELink` 的公开方法、操作游戏对象 | 不要阻塞（会卡住整个游戏） |
| WebRTC 原生线程 | `PeerSession` 的各回调 | 快速处理、把数据交给隧道 | 不要直接改游戏状态；回调里的 `ByteBuffer` 返回后即失效，必须复制 |
| Paho MQTT 线程 | `SignallingClient` 的监听器 | 解析消息、转交 `P2PSession` | 不要在这里做耗时的网络等待 |
| identity 单线程 | `IdentityService` | 依次执行账号相关的 HTTP 请求 | 结果通过回调返回，回调同样运行在这个线程 |
| 隧道线程（每条流 2 个） | `TunnelStream` | 阻塞式读写 socket、打帧/解帧 | 绝不能把这些读写放到游戏主线程 |

需要"从后台线程回到游戏线程"时用：
`source.getServer().execute(() -> …)`（示例见 `ELinkCommand.replyLater`）。

## 7. 调试技巧

日志按模块打标签（第一个括号里的名字），直接搜这些关键字即可定位：

| 关键字 | 含义 |
| --- | --- |
| `elink/config` | 配置读写、加密存储、令牌迁移 |
| `elink/signalling` | MQTT 连接、订阅、消息收发 |
| `elink/session` | 房间成员、账号挑战、协商发起、被忽略的消息 |
| `elink/rtc` | 原生库加载、数据通道、连接状态 |
| `elink/tunnel` | 隧道监听端口、每条流的建立与关闭、背压 |
| `elink/identity` | 登录、令牌刷新、`join`/`hasJoined` |
| `elink/lan` | 局域网广播（多人游戏列表里的条目） |
| `elink/platform` | 当前运行在哪个加载器上 |

排查顺序建议：
`elink/rtc`（原生库加载了吗）→ `elink/signalling`（连上 broker 并订阅了吗）→ `elink/session`（双方互相看到
了吗、是否被房间密钥或账号校验拦住）→ `elink/tunnel`（流建立了吗、是否被背压丢弃）。

## 8. 术语表

| 术语 | 说明 |
| --- | --- |
| broker | MQTT 服务器，只用来交换信令；默认用公共的 `broker.emqx.io` |
| 主题（topic） | MQTT 里的"频道名"，本模组用 `<前缀>/<房间码>` 以及其下的 `/presence` |
| 信令 | 建立 WebRTC 连接前要交换的信息（offer / answer / ICE），走 MQTT |
| SDP | 描述"我支持哪些编码、我的连接参数"的文本；offer 与 answer 都是 SDP |
| ICE / candidate | 打洞用的候选地址（本机地址、公网映射地址、中继地址……） |
| STUN | 帮你看清"我在公网看起来是什么地址"的服务器 |
| TURN | 打洞失败时的中继服务器（对称 NAT 场景需要） |
| DataChannel | WebRTC 提供的双向、可靠、有序的数据管道，隧道跑在它上面 |
| 帧（frame） | 隧道里的一次发送单位：`[streamId][type][载荷]` |
| 流（stream） | 一条被复用到隧道上的 TCP 连接，用 streamId 区分 |
| 托管方 / 加入方 | 托管方共享自己的世界（拨号 `127.0.0.1:<游戏端口>`）；加入方本地监听端口给玩家连 |
| 安装 ID | 每份游戏安装固定的随机 ID，用于区分对端、决定谁先发起协商 |
| 房间码 / 房间密钥 | 房间码决定 MQTT 主题；房间密钥证明"有资格进这个房间" |
| DPAPI | Windows 的密钥保护接口，本模组用它包裹加密主密钥，使其与当前 Windows 账户绑定 |

## 9. 注释约定

为了降低接手成本，代码统一这样写注释：

- **类级 Javadoc**：这个类负责什么、在整体流程里的位置、谁调用它、线程上的注意事项；
- **公开方法**：中文 Javadoc，写清参数、返回值、副作用（例如"会写配置文件"）；
- **复杂分支 / 协议细节**：行内中文注释，重点写**为什么**（例如"为什么要等背压"、"为什么要缓存 ICE
  candidate"），而不是把代码字面意思重复一遍；
- **加载器差异**：写在 `/*? if fabric {*/ … /*?}*/` 这类 Stonecutter 条件块里，块内只用 `//` 行注释
  （因为整块在其它加载器节点里处于注释状态，Javadoc 的 `*/` 会提前结束注释）。

新增文件请沿用同样的风格；改动协议（`SignalMessage`、`TunnelFrame`）时请同步更新
[`docs/architecture.md`](architecture.md) 与本文档。
